# Security review

## Continente MCP add-on 1.0.0

Reviewed 2026-11-03 before release (high-risk change: agent tokens, remote access, Continente account and
session). Scope: the whole add-on (`continente_mcp/`), its workflows and the hand-off with Cesto 2.0.0.
Verdict: **no Critical or High findings; release allowed.** Medium findings are accepted with the reasons below.

| # | Area | Finding | Severity | Status |
|---|---|---|---|---|
| 1 | Authentication | `/mcp` needs a token (`Authorization: Bearer cmcp_…` or `X-Continente-MCP-Token`); 401 otherwise, before the body is parsed into an MCP call. Tokens are 32 random bytes (base64url), compared by SHA-256 hash lookup; only the hash is stored (`/data/tokens.json`, 0600, atomic write). A token is returned once, in the create response to the HA-admin page, and never logged (`test/admin.test.ts` asserts it is absent from logs, status and later responses). | None | OK |
| 2 | Authorisation | The page and `/api/admin/*` answer only from the ingress proxy address and, when HA forwards a user, only for `system-admin` members; from the LAN they are 403. State-changing admin calls require a JSON content type, so cross-site forms cannot reach them; no CORS headers are ever sent. | None | OK |
| 3 | Ingress identity | A request from the ingress address without `X-Remote-User-*` headers is treated as an admin, as in Cesto. Only the Supervisor uses that address and it always forwards the HA user on ingress sessions. | Low | Accepted |
| 4 | Checkout and payment | `ToolPolicy` lists and calls only tools in the reviewed snapshot; checkout/payment/order-placing/delivery-slot/voucher/coupon/billing/card-like names also need `allow_checkout` (default false; only an explicit `true` enables it). The pinned continentept-mcp has no checkout or payment tool. Coupon and voucher tools (`list_coupons`, `set_cart_coupons`) are never exposed, even with `allow_checkout` (`NEVER_EXPOSED_TOOL`). The build fails if the installed package's tools differ from the snapshot. | None | OK |
| 5 | Cart changes | Every token may change the cart (as requested). Each change is logged as `[cart] agent="…" tool=… product=… quantity=… status=…`; names are restricted to letters, digits, space, `._-`, so log lines cannot be forged. Cart calls are never retried. | None | OK |
| 6 | Abuse | 120 calls a minute per token, at most 50 waiting calls, 1 MB body limit; one serial queue, priority tokens first. | None | OK |
| 7 | Token requests through `/share` | Any add-on that maps `/share` can write a request. Nothing is granted until an HA admin approves it on the page, where the request shows its name and fingerprint; Cesto shows the same fingerprint on its page. Requests are regular files ≤ 4 KB with a strict schema; symlinks are ignored. An admin who approves a request without comparing the fingerprint could give a token to another add-on. | Medium | Accepted: requires an installed add-on with `/share` access plus an admin approval; documented in the README and on the page. |
| 8 | Session hand-off through `/share` | Cesto 2.0.0 copies its old session and account (including the password file) to `/share/continente-mcp/import/` once; this add-on imports it within 5 s only if it has no session, and deletes it either way. During those seconds another add-on mapping `/share` could read it, or could plant its own session before Cesto does (only while this add-on has none). | Medium | Accepted: one-time, seconds long, needs an already-installed add-on with `/share` access (which in Home Assistant is trusted code); afterwards nothing secret stays in `/share`. Users without Cesto 1.x never use it. |
| 9 | Remote access | Remote use goes through HA ingress (HA authentication first, then the agent token). Port 8100 is meant for the LAN; the README says not to forward it. | Low | Accepted |
| 10 | Credentials | The Continente password is write-only (`/data/continente/credentials.env`, 0600), never returned, never logged. noVNC runs only during a sign-in, on localhost, proxied through ingress only. | None | OK |
| 11 | Public health | `/health` (no auth) shows version, session validity, sign-in state, queue length and the slug; no account, cart or token data. | Low | Accepted |
| 12 | Supply chain | `continentept-mcp` is installed from npm at a pinned version; updates come only through the daily workflow, which waits 72 h after an upstream release, inspects `tools/list` with `--ignore-scripts` and no browser, and auto-merges only when the tool contract is unchanged. Actions are pinned by SHA; `npm audit` reports 0 vulnerabilities. | Low | Accepted |
| 13 | Repository setting | The update workflow needs "Allow GitHub Actions to create and approve pull requests"; only `upstream-bump.yaml` requests `pull-requests: write`. | Low | Accepted |
| 14 | Repository content | No secrets, personal data, IP addresses or host names are committed (checked with a grep for addresses, e-mail addresses and tokens before release). | None | OK |

## 1.0.2 addendum

- Finding #8 (session hand-off through `/share`) re-checked after the import fix: the import window is unchanged in practice. It is open only while the add-on has no saved account and has never had a valid session. After the first valid session (marker `/data/session-established`) or once an account is saved, no hand-off is accepted. Severity stays Medium (accepted).

| # | Area | Finding | Severity | Status |
|---|---|---|---|---|

New fields: `per: dose`, `takePay`, `favoritesPromoted`, `cartSelection: unknown`, optional `search_products.promotion`. Nothing new touches checkout, payment, orders, slots or coupons. The live `tools/list` matches the committed snapshot. | None | OK |

| 20 | Supply chain | `continentept-mcp` 0.15.0 (npm integrity `sha512-KhlP8kkj…FyNg==`, published 2026-11-12). `npm audit` on its tree and on the add-on lockfile: 0 vulnerabilities. Installed by pinned version without an integrity pin in the Dockerfile and the CI contract job (unchanged from earlier releases). | Low | Accepted |
| 21 | GitHub Actions | Only change: the contract job also runs `test/session-binding.test.ts` with `REQUIRE_UPSTREAM=1`. No new permissions, secrets or triggers. | None | OK |

## 1.0.6 addendum

Reviewed 2026-11-21 (PR #21: session keep-alive, `unattended_sign_in`, Home Assistant session notification; `continentept-mcp` stays 0.16.1). Verdict: **no Critical or High findings; release allowed after the fixes below.**

| # | Area | Finding | Severity | Status |
|---|---|---|---|---|
| 26 | New permission | `homeassistant_api: true` gives the add-on a `SUPERVISOR_TOKEN` for the Home Assistant Core API. It is needed for the persistent notification when the session expires (`persistent_notification/create` and `dismiss`), the optional `binary_sensor.continente_mcp_session` (`POST /api/states/…`) and the restart check (`GET /api/`, `GET /api/states/<sensor>`). No `hassio_api` and no Supervisor API. The token goes only to the constant `http://supervisor/core/api` in the `Authorization` header. Logs carry only the path and the HTTP status or error name, never the token. | Low | Accepted |
| 27 | Token scrubbing | `index.ts` first reads `SUPERVISOR_TOKEN` (and removes `HASSIO_TOKEN`), then deletes it from `process.env` before anything is spawned. Every child process gets an explicit allowlist from `childEnv` (`PATH`, `HOME`, `LANG`, `LANGUAGE`, `LC_*`, `TZ`, `TMPDIR`, `NODE_ENV`, `DISPLAY`, `PLAYWRIGHT_*`, `CONTINENTE_*`, `XDG_*`) plus its own variables. That covers continentept-mcp, the keep-alive process, the page sign-in, Xvnc, websockify and, through them, Chromium. Unit tests check each spawn path with a fake token set. The image smoke test sets a fake token and scans `/proc/*/environ` of every other process while the gateway's continentept-mcp answers a search and while Xvnc, websockify and a headed Chromium run with the allowlisted environment. | Medium | Fixed |
| 28 | Residual risk | Code execution inside the container still reaches the token: the gateway's own `/proc/<pid>/environ` keeps the initial environment, and s6 keeps `/var/run/s6/container_environment/SUPERVISOR_TOKEN`. That is the case for every add-on with `homeassistant_api`. Scrubbing keeps the token from a compromised Chromium renderer or continentept-mcp that cannot read those files. It does not protect against root in the container. | Low | Accepted |
| 29 | Keep-alive cannot sign in | Verified in the 0.16.1 source. `loadSettings` lets an environment variable win even when empty. `loginWithCredentials` returns false ("Login skipped") without email and password, before any browser is started. So the keep-alive check always runs in a continentept-mcp with `CONTINENTE_PASSWORD=''`: the main process when `unattended_sign_in` is off (it then has none either), otherwise a short-lived separate process (`probeEnv`). A test against the installed 0.16.1 `loadSettings` shows no credentials for both environments while `credentials.env` holds a password, and credentials still present for the server with the option on and for the page sign-in. The check is a single `get_cart` (read-only), in the background queue lane. It stops at the first `not_authenticated` and at `session_keepalive_max_hours`, which is 1–12 with no "no limit" value. A check is abandoned after 60 s (SDK request timeout 55 s; a process still starting is closed). No captcha or "Não sou um robô" handling exists anywhere. | None | OK |
| 30 | Cookies | 0.16.1 writes `session.json` only after a sign-in (`AuthenticationClient`), never after normal requests. The main process loads it into its browser context and closes the browser after 5 idle minutes. A separate check process therefore sends the same saved session cookie as the main process after any idle period. Cookies the site rotates inside an open browser (e.g. Cloudflare's `__cf_bm`) are not shared, but they are not the session. With `unattended_sign_in` off, the check uses the main process anyway. | Info | OK |
| 31 | Public health | `/health` gains only `session_keepalive.enabled` and `ha_notification`, which Cesto needs. `unattended_sign_in` and the keep-alive state and next check time are on the admin status (ingress, HA administrators). | Low | Accepted |
| 32 | Coupons and checkout | Unchanged: `list_coupons` and `set_cart_coupons` are never listed or called for any token, with or without `allow_checkout`, and checkout-like tools stay behind `allow_checkout` (default off). | None | OK |
| 33 | Supply chain | `continentept-mcp` is still installed by pinned version (`npm install -g`), without a lockfile for its dependency tree (see #20). Moving it to a committed lockfile with `npm ci` would also need the daily upstream-bump workflow and its script to regenerate that lockfile, so it is left for a separate change. | Low | Accepted |
